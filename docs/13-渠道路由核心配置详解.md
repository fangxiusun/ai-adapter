# 渠道路由核心配置详解

本文档整理并合并以下三个配置项的代码行为、路由规则与实际生效方式：

- `enabled`
- `default_model`
- `aliases`

适用范围：`channels` 下的渠道配置与 `models` 下的模型配置。

---

## 1. 背景

在 `ai-adapter` 中，客户端请求并不是手工指定某个渠道，而是通过请求中的模型名自动路由到合适的渠道。

一个渠道是否参与路由、当模型未命中时如何兜底、客户端传入的模型别名如何映射到真实上游模型，主要由以下三个配置共同决定：

- `enabled`：控制渠道是否参与路由
- `default_model`：控制默认渠道的兜底模型，以及渠道内模型回退
- `aliases`：控制客户端模型别名到真实模型 ID 的映射

这三个字段都不是纯展示字段，均在实际代码路径中参与判断。

---

## 2. 配置位置

### 2.1 渠道级配置

```yaml
channels:
  - id: "mimo"
    name: "MiMo"
    enabled: true
    default_model: "mimo-v2.5-pro"
```

其中：

- `enabled` 是渠道级配置
- `default_model` 也是渠道级配置

### 2.2 模型级配置

```yaml
models:
  - id: "deepseek-v4-flash"
    aliases:
      - "deepseek-chat"
      - "deepseek-reasoner"
```

其中：

- `aliases` 是模型级配置

---

## 3. 三个字段的职责概览

| 配置项 | 层级 | 作用 | 是否实际生效 |
|---|---|---|---|
| `enabled` | channel | 控制渠道是否参与路由与候选选择 | 是 |
| `default_model` | channel | 请求模型未命中时的兜底模型；也用于渠道内模型解析回退 | 是 |
| `aliases` | model | 接收客户端别名请求，并映射到真实模型 ID | 是 |

可以把三者理解为：

- `enabled`：这个渠道能不能上场
- `default_model`：上场后，如果模型名不匹配，用哪个模型兜底
- `aliases`：客户端说的是外号，系统如何认出它本尊是谁

---

## 4. `enabled` 的作用与生效方式

### 4.1 配置含义

```yaml
channels:
  - id: "deepseek"
    enabled: true
```

`enabled` 用来控制某个渠道是否参与模型路由。

- `true`：渠道可参与路由
- `false`：渠道不参与路由

### 4.2 实际生效点

代码定义：

- `internal/config/config.go:62`

路由时的实际生效点包括：

1. 构建模型索引时跳过禁用渠道
   - `internal/channel/channel.go:198`

2. 选择匹配渠道时再次过滤禁用渠道
   - `internal/channel/channel.go:151`

3. 默认渠道回退时也要求渠道启用
   - `internal/channel/channel.go:159`
   - `internal/channel/channel.go:230`

### 4.3 实际效果

当某个渠道 `enabled: false` 时：

- 不会进入模型索引
- 不会成为候选渠道
- 不会参与默认回退
- 即使 Web UI 中仍能看到该渠道，也只是展示，不代表它会被请求实际使用

### 4.4 结论

`enabled` 是路由入口的硬开关，**有明确且直接的实际效果**。

## 5. `default_model` 的作用与生效方式

### 5.1 配置含义

```yaml
channels:
  - id: "mimo"
    default_model: "mimo-v2.5-pro"
```

`default_model` 表示：

- 当请求模型未命中时，使用哪个模型作为回退目标

### 5.2 代码定义

- `internal/config/config.go:66`

### 5.3 生效链路

#### 场景一：全局路由未命中任何渠道

如果客户端请求的模型没有命中任一启用渠道的 `models` 或 `aliases`，系统会回退到默认渠道的 `default_model`：

- `internal/channel/channel.go:159`
- `internal/channel/channel.go:230`

这里的“默认渠道”是 `ChannelManager` 初始化时的第一个渠道：

- `internal/channel/channel.go:54`

也就是说，当前实现中：

- 默认渠道 = `channels` 列表中的第一个渠道
- 全局兜底时用的是“默认渠道的 `default_model`”

#### 场景二：渠道已选定后的模型解析回退

当某个渠道已经被选中后，系统会调用 `ResolveModel()` 解析最终上游模型：

- `internal/channel/channel.go:283`

解析规则是：

1. 先查客户端传入模型名是否命中当前渠道的 `models` 或 `aliases`
2. 如果未命中，则回退到该渠道自己的 `default_model`

对应代码：

- 命中客户端模型：`internal/channel/channel.go:284`
- 回退到渠道默认模型：`internal/channel/channel.go:295`

### 5.4 转发时是否真正替换模型

是的。

在代理实际转发前，会把请求体中的 `model` 改成最终解析出的真实上游模型 ID：

- `internal/proxy/handler.go:261`
- `internal/proxy/handler.go:265`
- `internal/proxy/handler.go:289`
- `internal/proxy/handler.go:293`
- `internal/proxy/helpers.go:202`

这说明 `default_model` 不是只影响“选中哪个 channel”，而是会直接影响最终发给上游的模型值。

### 5.5 需要注意的边界

`default_model` 的生效有两个层面：

1. **全局候选选择层面**
   - 只对默认渠道的兜底有决定作用

2. **单个渠道内部模型解析层面**
   - 对已选中渠道来说，它自己的 `default_model` 确实会作为模型回退值

因此，`default_model` 不是“所有渠道平等参与的全局默认模型”，而更像：

- 默认渠道的全局兜底模型
- 以及各自渠道内部的模型兜底值

### 5.6 结论

`default_model` **有实际作用**，并且会影响最终上游请求中的模型字段。

## 6. `aliases` 的作用与生效方式

### 6.1 配置含义

```yaml
models:
  - id: "deepseek-v4-flash"
    aliases:
      - "deepseek-chat"
      - "deepseek-reasoner"
```

`aliases` 表示这个模型可以接受多个“客户端请求名”。

客户端可以传：

- `deepseek-v4-flash`
- `deepseek-chat`
- `deepseek-reasoner`

系统会把它们都识别为同一个真实模型。

### 6.2 代码定义

- `internal/config/config.go:113`

### 6.3 生效链路

#### 第一步：渠道内部模型映射

初始化 channel 时，系统会把：

- 模型 `id`
- 该模型的全部 `aliases`

都写入同一个映射表，并且 alias 指向原模型配置：

- `internal/channel/channel.go:67`
- `internal/channel/channel.go:70`

这意味着：

- `ch.models["deepseek-v4-flash"]` 可以找到模型
- `ch.models["deepseek-chat"]` 也可以找到同一个模型
- `ch.models["deepseek-reasoner"]` 也可以找到同一个模型

#### 第二步：构建路由索引

系统构建 `modelIndex` 时，也会把 alias 一起注册进去：

- `internal/channel/channel.go:201`
- `internal/channel/channel.go:204`

因此客户端请求别名时，也能直接命中对应渠道。

#### 第三步：解析为真实模型 ID

真正命中 alias 后，`ResolveModel()` 返回的不是 alias，而是模型本体的真实 `id`：

- `internal/channel/channel.go:283`

也就是说：

- 输入：`deepseek-chat`
- 解析结果：`deepseek-v4-flash`

#### 第四步：转发前替换请求体模型名

代理在转发到上游之前，会用真实模型 ID 替换请求体中的 `model` 字段：

- `internal/proxy/handler.go:262`
- `internal/proxy/handler.go:265`
- `internal/proxy/helpers.go:202`

因此最终发给上游的不是 alias，而是规范化后的模型 ID。

### 6.4 实际效果示例

配置：

```yaml
models:
  - id: "deepseek-v4-flash"
    aliases:
      - "deepseek-chat"
      - "deepseek-reasoner"
```

客户端请求：

```json
{
  "model": "deepseek-chat",
  "messages": [
    {"role": "user", "content": "hello"}
  ]
}
```

系统行为：

1. 使用 `deepseek-chat` 命中 `deepseek` 渠道
2. 将 `deepseek-chat` 解析为真实模型 `deepseek-v4-flash`
3. 转发前把请求体中的 `model` 替换为 `deepseek-v4-flash`
4. 向上游发送规范模型 ID

### 6.5 附加作用：Header Policy 也支持 alias

`aliases` 不只影响渠道路由，也影响模型级 Header Policy 匹配。

对应代码：

- `internal/headerpolicy/engine.go:58`

这表示：

- 如果某模型定义了请求头/响应头策略
- 客户端即使使用 alias 请求
- 仍然会命中该模型对应的 Header Policy

### 6.6 结论

`aliases` **明确生效**，本质上是一个“客户端请求名兼容层”。

## 7. 三者组合后的完整路由过程

下面用一个完整流程说明三者如何共同生效。

### 7.1 示例配置

```yaml
channels:
  - id: "mimo"
    enabled: true
    default_model: "mimo-v2.5-pro"
    models:
      - id: "mimo-v2.5-pro"
      - id: "mimo-v2.5"

  - id: "deepseek"
    enabled: true
    default_model: "deepseek-v4-pro"
    models:
      - id: "deepseek-v4-flash"
        aliases:
          - "deepseek-chat"
          - "deepseek-reasoner"
```

### 7.2 情况一：请求真实模型 ID

客户端请求：

```json
{"model": "deepseek-v4-flash"}
```

结果：

- 命中 `deepseek` 渠道
- 直接解析为 `deepseek-v4-flash`
- 发给上游的也是 `deepseek-v4-flash`

### 7.3 情况二：请求 alias

客户端请求：

```json
{"model": "deepseek-chat"}
```

结果：

- alias 命中 `deepseek` 渠道
- 解析为真实模型 `deepseek-v4-flash`
- 发给上游时替换为 `deepseek-v4-flash`

### 7.4 情况三：请求未知模型

客户端请求：

```json
{"model": "unknown-model"}
```

结果：

- 所有启用渠道均未命中
- 回退到默认渠道（即第一个渠道）`mimo`
- 使用 `mimo.default_model = mimo-v2.5-pro`
- 发给上游的模型变为 `mimo-v2.5-pro`

### 7.5 情况四：渠道被禁用

如果：

```yaml
channels:
  - id: "deepseek"
    enabled: false
```

那么即使客户端请求：

```json
{"model": "deepseek-chat"}
```

结果也会是：

- `deepseek` 不参与路由
- alias 不会命中该渠道
- 最终进入默认渠道回退，或返回无可用渠道错误

## 8. 常见误区

### 8.1 误区：`enabled` 只是 UI 展示开关

不是。

它会直接影响模型索引和候选路由，属于真正的逻辑开关。

### 8.2 误区：`default_model` 是所有渠道共享的全局默认模型

不是。

当前实现下，它最主要的全局兜底作用来自默认渠道，也就是 `channels` 数组中的第一个渠道。

### 8.3 误区：`aliases` 命中后会上游继续使用 alias

不是。

命中 alias 后，系统会将其规范化为真实模型 `id`，然后再发往上游。

### 8.4 误区：只要配置了 `aliases` 就一定能路由成功

不一定。

还要求：

- 所在渠道 `enabled: true`
- 该渠道已经被纳入路由索引
- 请求最终存在可用的接口能力 URL 或可转换路径

---

## 9. 配置建议

### 9.1 关于 `enabled`

- 临时下线渠道时，优先改 `enabled: false`
- 不要通过删除配置来实现临时停用

### 9.2 关于 `default_model`

- 建议为每个渠道配置一个稳定、确定可用的默认模型
- 尤其是默认渠道，应认真设置 `default_model`
- 默认渠道建议放在 `channels` 列表第一位，并确保它是最稳妥的兜底渠道

### 9.3 关于 `aliases`

- 可用于兼容旧模型名、第三方 SDK 默认模型名、历史调用名
- 建议 alias 语义和真实模型能力保持一致，避免“名字像推理模型，实际却映射到非推理模型”的歧义

## 11. 总结

`enabled`、`default_model`、`aliases` 三个字段共同构成了渠道路由的核心配置语义：

- `enabled` 决定渠道能不能参与路由
- `default_model` 决定未命中时用哪个模型兜底
- `aliases` 决定客户端模型别名如何映射到真实模型 ID

当前实现下，这三个字段都已经接入实际代码路径，并对最终路由和上游请求产生真实影响。
