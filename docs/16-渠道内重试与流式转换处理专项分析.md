# 渠道内重试与流式转换处理专项分析

> 初始分析日期：2026-07-25  
> 实施更新日期：2026-07-26  
> 分析与实施范围：`internal/proxy/forward.go`、`internal/proxy/stream.go`，以及全项目同类重试、Key 状态、跨渠道故障转移、协议流转换和 Fanout 路径。

本文分成两部分：第 0 节记录最终配置契约、已实施行为、测试与剩余边界；第 1 节以后保留修改前的代码审计，作为问题来源和设计依据。阅读当前行为时以第 0 节为准。全局 Channel/Key 交错调度的完整实施说明见 `docs/18-全局Channel-Key交错调度设计与实现.md`。

## 0. 实施结果与最终契约

### 0.1 方案评估

本次修改思路整体可行。需要明确的两个边界是：

1. `max_rotation_rounds` 是每个 Channel 的完整 Key 轮次上限。会提前结束的条件只有成功、请求取消、总超时、已提交的流错误或没有可用 Key；已删除的连续失败阈值不会再截断轮次。
2. 实时流一旦向客户端提交 HTTP 200 或首个 SSE 事件，就不能安全地换 Key 重放；提交后的解析错误只能终止当前流并记为流错误。提交前的 HTTP 状态错误仍按正常状态机处理。

除此之外，各项修改之间没有配置或状态语义冲突。

### 0.2 最终状态码契约

| 上游结果 | 当前 Key | 请求级状态 | 渠道级结果 | ChannelHealth |
|---|---|---|---|---|
| 2xx 且处理成功 | `ReportSuccess`，连续错误清零 | 请求结束 | 成功 | 重置渠道连续失败 |
| 401 | 永久跳过；`RequestCount`、401 计数各加一 | 请求级连续网络/5xx 计数清零；换下一个 Key | Key 耗尽后才失败 | 不累计 |
| 429 | 记录 429，不触发 Key 跨请求暂停 | 本请求冷却到 `retry_delay_429_ms` 到期；到期后可在后续轮次重新候选 | 继续轮转 | 不累计 |
| 400 | Key 统计按 429 处理 | 与 429 相同地进入请求级 cooldown；当前轮换下一个 Key | 不写中间 429；当前渠道轮次耗尽后才向外层返回最终错误 | 不累计 |
| 其他 4xx | 按实际状态记录 | 请求级连续网络/5xx 计数清零 | 立即返回 `FailoverError`，外层可切换渠道 | 不累计 |
| 5xx | 记录 5xx，不触发 Key 跨请求暂停；只在当前轮跳过 | 立即交错到下一个 Channel；下一轮可再次使用 | 全部路由耗尽后失败 | 累计 |
| 连接错误 | 记录网络错误 | 立即交错到下一个 Channel | 全部路由耗尽后失败 | 累计 |
| 流解析/写入错误 | 记录 `ErrorStream`，不记成功 | 若 HTTP 200 已提交则终止流 | 不能再 Failover | 不累计为渠道 5xx/连接错误 |

“401 清零”指清零本请求、当前渠道内的连续网络/5xx 计数；401 仍会保留 Key 自身错误统计，并把 Key 永久标记为不可用。

### 0.3 真正的完整轮次

全局调度器为每个 Channel 维护三类请求级状态：

- `attempted`：当前轮已尝试的 Key，每轮每个可用 Key 最多一次。
- `cooldownUntil`：429 Key 的请求级冷却截止时间。
- `round`：从 1 开始，完成所有 Channel 的当前轮后递增，并清空各自的 `attempted`。

Key 选择直接调用 `KeyPool.NextExcluding`，五种选择策略都会在候选集合生成阶段排除当前轮已尝试和仍处于 429 冷却的 Key，不再出现“策略反复选中已排除 Key”的问题。

429 不再执行阻塞式 `time.Sleep`。当没有其他候选 Key 时，状态机使用 Context 感知的 timer 等待最早冷却到期；客户端取消或总超时会立即中断等待。冷却到期只解除 429 排除，不绕过“每轮每 Key 最多一次”的约束。

每个 pass 对每个 Channel 最多选择一个 Key，因此顺序是 `A/key1 -> B/key1 -> A/key2 -> B/key2`。5xx 和连接错误不会永久加入请求级黑名单：它们只存在于当前轮 `attempted` 中，开始下一轮后可重新候选。401 的永久跳过由 `KeyState.PermanentlySkipped` 管理，跨请求生效。

### 0.4 超时契约

`retry.max_total_wait_ms` 在单 Channel 遍历中通过派生 Context deadline 覆盖：

- Key 选择和 429 冷却等待；
- 建立上游请求；
- 读取非流式响应；
- 消费流式响应。

多 Channel 遍历使用 `failover.total_timeout_ms` 作为所有 Channel/Key 对共享的硬截止时间。HTTP 客户端的 `request_timeout_ms` 也会独立生效，以最先到期者为准。

### 0.5 延迟统计

当前明确区分两种延迟：

| 指标 | 起止范围 | 用途 |
|---|---|---|
| 系统端到端总延迟 | Handler 接受请求到响应处理结束 | 请求日志、数据库统计、Prometheus/汇总统计 |
| Key 单次尝试延迟 | 某个 Key 发起 HTTP 请求到该次响应读取/流处理结束 | `KeyState.TotalLatencyMs`、`AvgLatencyMs`、`least-latency` 选择 |

失败尝试也记录自己的单次延迟。系统日志不再信任调用点传入的局部耗时，而是根据请求入口保存的开始时间重新计算，避免把 Key 尝试耗时误当成整个请求耗时。Fanout 也为每个并发尝试独立统计，不再把整个并发等待时间重复记到赢家 Key。

### 0.6 实时跨协议流

跨协议流已经从“完整聚合为 `ChatResponse` 后再合成流”改为实时增量管道：

```text
Responses / Claude / Gemini 上游 SSE
  -> 严格解析并逐事件转换为 Chat SSE
  -> io.Pipe（有背压，不保存完整字节流）
  -> 逐事件转换为目标 Responses / Claude / Gemini SSE
  -> 客户端
```

目标为 Chat 时省略第二段转换，直接输出实时 Chat SSE。转换器现在检查：

- Context 取消和截止时间；
- 非法 JSON；
- `bufio.Scanner` 错误；
- 缺失协议终止事件；
- JSON 编码和下游写入错误。

只有完整处理成功才调用 `ReportSuccess`。Responses 上游只有 `response.completed` 完整快照、没有 delta 时，会把快照中的正文、推理和工具调用补发成 Chat 增量，再发送 finish chunk 和 `[DONE]`。

原生同协议流保持透明代理职责：检查 `io.Copy` 传输错误，但不解析协议终止事件。因此它能发现连接/写入失败，不能证明上游 SSE 语义完整。

### 0.7 Fanout 一致性

Fanout 不执行串行轮次，它的 `count` / `wait_all` 仍决定并发竞速行为，但共享的统计和错误语义已经统一：

- 非流式每个并发 attempt 记录自身耗时。
- 流式 2xx 赢家只在完整复制/转换后记成功。
- 取消落选请求不记网络错误；2xx 落选响应保持中性。
- 每个流式 attempt 使用独立 Context，取消落选请求不会中断赢家 Body。
- 400 对 Key 按 429 统计，但不直接向客户端写 429；Fanout 全部失败时保留代表性的上游 400。
- 全部失败时，仅连接错误和 5xx 会设置 `AffectsChannelHealth`。

因为 Fanout 是并发竞速而非串行轮询，`max_rotation_rounds` 与 `retry_delay_429_ms` 不适用于 Fanout；需要轮次/429 请求级冷却时应关闭该渠道的 Fanout。

### 0.8 ChannelHealth 契约

`FailoverError` 增加 `AffectsChannelHealth`。外层只有在该字段为 true 时调用 `ReportChannelFailure`，当前只由明确的连接错误、上游 5xx，以及包含这些失败的 Fanout 全失败结果设置。401、429、400、其他 4xx、客户端取消和协议转换错误不会把渠道标成不健康。

### 0.9 已知边界与未纳入项

1. 实时流在 HTTP 200 提交后无法安全重试，这是 HTTP 流式响应的协议边界，不是状态机遗漏。
2. 429 使用固定配置延迟，仍未解析上游 `Retry-After`，也没有指数退避或抖动。
3. 非流式 `io.LimitReader` 恰好达到上限时仍不能区分完整响应与被截断响应。
4. Fanout 是并发原子模式，不参与交错轮次；开启跨 Channel failover 时会旁路 Fanout。
5. 429 和 5xx 不参与 Key 跨请求暂停；401 仍永久跳过，其他 Key 级错误和流错误仍可能按 `consec_error_threshold` 触发暂停。

### 0.10 验证覆盖

新增或更新的测试覆盖：Channel/Key 交错顺序、同模型成功路由优先、首选失败后完整遍历、多轮、400/429 cooldown、401 永久跳过、其他 4xx 和 5xx 切换、全部状态分类、未知模型 fallback 日志、流截断/坏 JSON、Responses/Claude/Gemini 实时转换，以及 Fanout 400/赢家/取消语义。

## 1. 结论摘要（修改前基线）

目标代码实现的是“渠道内按 Key 重试 + 必要时向外层返回 `FailoverError`”机制，而不是普通的一次性 HTTP 转发。请求会先转换成上游协议，在同一渠道内挑选 Key、发送请求、按状态码更新 Key 健康状态；仍不能完成时，才由外层决定是否切换渠道。

全项目共发现四套高度相似的串行重试循环：

| 路径 | 位置 | 使用场景 |
|---|---|---|
| 原生转发 | `internal/proxy/forward.go:75-212` | 上下游接口相同，兼容非流式与流式 |
| 转换后非流式 | `internal/proxy/forward.go:216-342` | 上下游接口不同，完整响应转换 |
| Chat 源流式转换 | `internal/proxy/stream.go:99-229` | Chat SSE 转 Responses、Claude 或 Gemini |
| 跨协议流式链 | `internal/proxy/stream.go:231-353` | Responses、Claude、Gemini 流先汇聚为 Chat，再重新发流 |

此外还有两套 Fanout 并发路径：`fanoutForward` / `convertedFanoutForward` 和 `fanoutStreamForward`，底层位于 `internal/channel/fanout.go`。它们不使用上述串行重试状态机，但共享 Key 健康统计，存在另一组一致性问题。

当前实现存在多项确定性缺陷。最重要的结论如下：

1. `max_rotation_rounds` 实际限制的是循环尝试次数，不是“尝试完全部 Key 的轮数”；请求内排除表从不清空，所以不存在第二轮 Key 轮转。
2. `getNextKey` 没有使用项目中已有的 `KeyPool.NextExcluding`，而是在选出 Key 后才判断排除。`least-errors`、`least-latency`、`least-rate-limited` 会反复选中同一个已排除 Key，可能错误地报告“无可用 Key”；`random` 也可能随机漏掉仍可用的 Key。
3. 流式链路会先完整读取上游流，再向客户端输出，失去实时流式效果，并产生无上限内存占用、首字延迟和重复计费风险。
4. Chat、Claude、Gemini 的流解析器普遍忽略 JSON 解析错误和 `scanner.Err()`，截断流或空流仍可能被标记为成功；只有 Responses→Chat 路径检查了 `scanner.Err()`。
5. 多处统计把“整个重试过程耗时”记到最终成功 Key，且部分流复制错误被忽略后仍调用 `ReportSuccess`，会污染 Key 健康状态和 `least-latency` 选择结果。
6. 400 被统一改写成 503 并计入 Key 错误/暂停；其他 4xx 又不在当前渠道继续换 Key，而是立即返回跨渠道错误。行为与现有文档及代码注释均不一致。
7. `max_total_wait_ms` 只在每轮开始时检查，无法中断正在进行的 HTTP 请求或 `time.Sleep`，不是硬超时。
8. 旧配置 `max_retries`、`retry_delay_ms` 和若干辅助字段/函数已不参与执行，现有文档仍将其描述为有效能力。

## 2. 整体调用链

入口在 `internal/proxy/handler.go`：

```text
HTTP Handler
  -> failoverLoop（候选渠道选择、跨渠道故障转移）
    -> dispatch（决定原生转发或协议转换）
      -> 渠道内串行重试循环
        -> RetryState（本次请求的排除表、尝试计数、总耗时）
        -> KeyPool / KeyState（跨请求持久健康状态）
      <- nil：已成功，或错误已直接写给客户端
      <- FailoverError：允许外层尝试下一渠道
```

这里同时存在两层“连续失败”概念：

- `RetryState.consecFails`：单次请求、单个渠道内的临时计数，阈值来自全局 `failover.consecutive_fail_threshold`。
- `KeyState.ConsecErrors`：跨请求、单个 Key 的健康计数，阈值来自渠道 `retry.consec_error_threshold`，达到阈值后暂停 Key。

另有 `ChannelHealth.consecFailures` 用于跨请求暂停整个渠道，但其阈值固定为 3、恢复时间固定为 60 秒，并未使用 `failover.consecutive_fail_threshold`。

## 3. `forward.go:233-319` 逐段原理与影响

### 3.1 路径与状态初始化（233-235）

- `upstreamPathForInterface(source, model, false)` 根据上游原生接口计算 URL path。
- `newRetryState` 记录开始时间、请求内排除 Key 集合、最大尝试配置、429 等待时间和连续渠道失败阈值。
- `result` 暂存最终成功的上游响应。

影响：请求转换结果 `sourceBody` 在所有 Key 间复用，避免重复转换；与此同时，如果请求本身有协议转换错误，每个 Key 都会收到相同的错误请求。

### 3.2 循环终止检查（236-239）

`checkRotationAndTimeout` 每进入一次循环就执行 `rounds++`，然后判断：

- `rounds > max_rotation_rounds`：返回 503。
- 已用时间达到 `max_total_wait_ms`：返回 504。

实际影响：默认 `max_rotation_rounds=3` 表示最多发起 3 次请求，不是 3 轮完整 Key 轮换。第四次循环在选 Key 之前终止。

### 3.3 Key 选择（240-243）

`getNextKey` 最多调用 KeyPool 的 `Next()` 共 `KeyPool.Size()` 次，拿到不在 `rs.excluded` 中的 Key。找不到时返回 503。

它同时考虑两类排除：

- KeyPool 全局状态：401 永久跳过、暂停尚未到期。
- RetryState 请求内状态：本次请求已经失败过的 Key。

影响：避免在同一请求中立即重复使用失败 Key。但筛选发生在 KeyPool 完成策略选择之后，对非轮询策略不可靠，详见第 8.2 节。

### 3.4 创建上游请求与 Header（244-257）

- URL 为渠道对应接口 Base URL 与 path 的拼接。
- 通过原客户端请求的 Context 创建 POST，因此客户端取消能传递给上游。
- 默认设置 JSON Content-Type 和 `Bearer <key>`。
- HeaderPolicy 可以加工其余请求头，但 `Content-Type`、`Authorization` 被保护。
- 普通日志和深度日志记录上游请求。

影响：每次换 Key 都创建独立请求，body 可安全重读。上游若不使用 Bearer 认证，只能依赖渠道/代理本身兼容这一约定，HeaderPolicy 不能替换受保护的 Authorization。

### 3.5 网络错误（258-268）

- `HTTPClient.Do` 失败后执行 `ReportError(key, 0)`，在 KeyState 中记为网络错误。
- 当前 Key 加入请求内排除表。
- `consecFails` 加一，达到阈值时返回 `StatusCode=0` 的 `FailoverError`，否则继续换 Key。

影响：外层 `sendError` 会把状态 0 规范化为 502。网络故障会同时影响 Key 健康和渠道故障转移；若多个 Key 共享同一 Base URL，逐 Key 重试通常无法消除渠道级网络故障，只会增加等待时间。

### 3.6 读取响应（270-276）

转换后非流式路径在判断状态码前，先把响应读到内存，最大为 `maxResponseBodyBytes()`，默认与请求体限制相同（默认 64 MiB），然后关闭 Body。

影响：

- 优点是通常能读尽响应体，使 HTTP 连接更容易复用，也保留了错误体用于 400/其他 4xx 日志。
- `io.LimitReader` 恰好读到上限不会返回“超限”错误，因此无法区分完整响应和截断响应。
- 读取错误只记录警告，后续仍按状态码继续；2xx 的部分响应可能进入 JSON 转换。
- 401、429、5xx 的大错误体也会先占用内存，和其他三套循环直接关闭 Body 的行为不同。

### 3.7 401（277-281）

- Key 被永久标记为跳过。
- 本次请求也排除该 Key。
- 立即尝试下一个 Key。

影响：适合处理明确的 Key 失效。该路径没有像另外三套循环那样把 `rs.consecFails` 清零，因此“5xx/网络错误 → 401 → 5xx/网络错误”会累计达到渠道失败阈值，四套实现不一致。

### 3.8 429（282-288）

- 记录限流并排除 Key。
- 固定等待 `retry_delay_429_ms` 后尝试下一个 Key。

影响：降低立即撞上限流的概率，但等待不是 Context 感知的，也不会被 `max_total_wait_ms` 中断；即使客户端已断开，仍可能睡满配置时间。代码不读取 `Retry-After`，也没有抖动或指数退避。

### 3.9 5xx（289-298）

- 记录 Key 的 5xx 错误并排除 Key。
- 请求级 `consecFails` 加一，达到全局阈值后结束当前渠道，否则换 Key。

影响：可以快速从故障渠道切换出去。但计数并非“相同状态码连续失败”，错误消息却使用最后一次状态拼成“连续 N 次该状态”；网络错误与不同 5xx 混合时，提示不准确。

### 3.10 400（299-305）

- 将 Key 记录为 400 错误。
- 上游 400 被映射为客户端 503，保留原始错误体到日志和响应。
- 直接写响应并返回 `nil`，不再换 Key、不跨渠道。

影响：当前测试明确固化了“上游 400 → 客户端 503”。这能隐藏上游协议不兼容，但也会把真实的客户端参数错误伪装成服务不可用，并可能暂停本来正常的 Key。外层看到 `nil` 还会调用 `ReportChannelSuccess`。

### 3.11 其他 4xx（306-313）

- 记录 Key 错误并加入请求内排除表。
- 清零请求级连续渠道失败计数。
- 立即返回 `FailoverError`，不在当前渠道继续尝试其他 Key。

影响：启用跨渠道故障转移时会切换渠道；未启用时直接向客户端返回对应 4xx。它与文档中“403/404/其他 4xx 先轮换当前渠道全部 Key”的描述不一致。

### 3.12 成功（315-319）

- 记录本次 HTTP 请求延迟。
- 调用 `ReportSuccess` 清空 Key 连续错误。
- 保存响应、Header、Key 和延迟，退出循环，随后进行 Source→Chat→Target 转换。

影响：只有转换也成功才最终给客户端 200。但转换失败时，当前代码不会给 Key 记成功或失败、不会记录延迟，也不会触发跨渠道切换，统计会漏掉这次已完成的上游调用。

## 4. `stream.go:244-352` 逐段原理与影响

### 4.1 请求、Key 轮换和 HTTP 状态处理（244-317）

这一部分与非流式循环基本同构：检查次数/超时、选择 Key、创建请求、处理网络错误、401、429、5xx、400 和其他 4xx。

主要差异：

| 项目 | 转换后非流式 | 跨协议流式链 |
|---|---|---|
| 错误体读取 | 所有状态先读，默认上限 64 MiB | 只读 400/其他 4xx，固定 64 KiB |
| 401 后 `consecFails` | 不清零 | 清零 |
| 失败响应连接复用 | 通常已读 Body | 401/429/5xx 直接关闭，通常不能复用连接 |
| 上游成功处理 | JSON 响应转换 | 完整消费上游流并汇聚 |

### 4.2 上游流捕获与汇聚（319-328）

- `io.TeeReader` 同时把上游字节写入深度调试捕获器。
- `accumulateStreamToChat` 按 source 类型调用 Responses、Claude、Gemini 或 Chat 流解析器。
- 在解析完成前不会向客户端写 Header 或任何响应字节。
- 解析器返回错误时，记录 `ReportStreamError`、排除 Key 并重新尝试。

设计目的：只有拿到一份完整、可转换的 ChatResponse 后才提交客户端响应，因此理论上可在流解析失败时安全换 Key。

实际影响：

- 这是一种“先缓冲完整结果，再伪装成流”的实现，客户端失去逐 Token 到达体验。
- 完整内容、推理文本和工具参数均在内存拼接，没有响应大小限制。
- 字符串反复 `+=` 对长输出可能产生较多复制和 GC 压力。
- 若重试，失败 Key 已经生成的 Token 会被丢弃，但仍可能产生上游费用；另一个 Key 会重新生成，结果也可能不一致。
- 只有 Responses→Chat 检查 `scanner.Err()`；Chat、Claude、Gemini 路径会忽略 scanner 错误和坏 JSON，空/截断响应可被当成成功，实际重试能力远弱于代码外观。

### 4.3 成功统计（329-331）

- 将 `rs.elapsed()` 记录为最终 Key 的延迟。
- 调用 `ReportSuccess`。
- 记录上游响应 Header。

影响：`rs.elapsed()` 包含之前失败 Key 的请求时间和 429 Sleep，不是最终 Key 自己的延迟，会污染平均延迟和 `least-latency` 策略。

### 4.4 客户端响应 Header 与 Flush（332-344）

代码构造一个 `flusher`，其中执行响应 HeaderPolicy 并调用 `http.Flusher.Flush()`；随后设置 SSE Header 并立即 `WriteHeader(200)`。

缺陷：响应 HeaderPolicy 只在后续首次写事件、调用 `flusher` 时执行，但此时 `WriteHeader(200)` 已提交 Header，策略修改通常不会再发送给客户端。相同问题也存在于 `streamFromChatSource` 和 `fanoutStreamForward`；原生流式路径则是在 `WriteHeader` 前应用策略。

### 4.5 重新发射目标协议流（345-350）

- 用 `MultiWriter` 同时写客户端和调试捕获器。
- `emitStreamResponse` 把完整 ChatResponse 重新编码为目标接口的流式外观。
- 从完整 ChatResponse 记录 Usage 和请求日志。

影响：重新发射不是原始流的等价转发，事件粒度、时序和部分语义会丢失：

- Chat 输出使用 `event: message`，结束事件输出为 `event: done` + JSON 字符串 `"[DONE]"`，不符合 OpenAI Chat 常用的纯 `data: ...` / `data: [DONE]` 格式。
- Chat 重新发射只带 content，丢失已汇聚的 reasoning、tool calls、usage 等字段。
- Responses 只发 `response.created` 和 `response.completed`，没有文本/tool delta 事件，且 created 中已经携带完整响应。
- Claude 的 `message_start` 携带完整内容，随后又逐块发送内容，可能与标准事件语义重复。
- Gemini emitter 写的是一行普通 JSON，但外层 Header 固定为 `text/event-stream`，协议与 Content-Type 不一致。

## 5. 四套串行循环的状态码行为对照

| 条件 | 原生转发 | 转换后非流式 | Chat 源流式转换 | 跨协议流式链 |
|---|---|---|---|---|
| 网络错误 | 排除、计数、可能跨渠道 | 同左 | 同左 | 同左 |
| 401 | 永久跳过、清零请求级计数 | 永久跳过、不清零 | 永久跳过、清零 | 永久跳过、清零 |
| 429 | 排除、固定 Sleep | 同左，但先读 Body | 同左 | 同左 |
| 5xx | 排除、累计渠道失败 | 同左，但先读 Body | 同左 | 同左 |
| 400 | 映射 503，停止 | 同左 | 同左 | 同左 |
| 其他 4xx | 立即返回 FailoverError | 同左 | 同左 | 同左 |
| 2xx 后处理错误 | 原生复制错误被忽略 | 转换失败直接响应，不 Failover | 转换写入错误普遍被忽略 | 部分解析器可重试，多数错误被忽略 |
| 成功延迟 | 整个 RetryState 耗时 | 最终单次请求耗时 | 整个 RetryState 耗时 | 整个 RetryState 耗时 |

## 6. Fanout 同类处理

### 6.1 非流式 Fanout

`Channel.Fanout` 并发选取 N 个 Key：

- `wait_all=false`：返回第一个 2xx，取消其余请求并在后台收集统计。
- `wait_all=true`：等全部结束，选择最快 2xx。
- 处理器随后直接转发，或做协议转换。

观察到的问题：

1. FanoutResult 不保留上游 Header，响应 HeaderPolicy 收到 `nil`，无法基于真实上游 Header 工作。
2. 固定读取最多 64 MiB，同样不能识别被 LimitReader 截断的响应。
3. 协议转换路径在选出 2xx 时已经把 Key 标记成功；后续转换失败也不会修正健康状态。
4. Fanout 完全绕过 `RetryState`，`max_rotation_rounds`、`max_total_wait_ms`、429 delay 对其不生效。

### 6.2 流式 Fanout

`Channel.FanoutStream` 以“最先返回 2xx Header”为赢家，处理器立即把赢家标记成功，再读取和转换 Body。

观察到的问题：

1. 赢家只证明 Header 为 2xx，不代表流体完整；后续复制/解析失败仍保持成功统计。
2. 取消后收集其他尝试时，只要 Key 非空就调用 `ReportError(key, 0)`，正常被赢家取消的请求也可能被记为网络错误，污染失败计数并触发暂停。
3. `fanoutStreamForward` 的响应 HeaderPolicy 同样在 `WriteHeader` 后才执行。

## 7. 配置的真实语义

| 配置 | 当前真实行为 | 文档/命名偏差 |
|---|---|---|
| `retry.max_rotation_rounds` | 单个渠道内重试循环最多允许发起的请求次数 | 不是完整 Key 轮数；排除表不会重置 |
| `retry.max_total_wait_ms` | 只在新一轮开始前检查的软上限 | 不能中断当前 HTTP 请求或 Sleep，不是硬上限 |
| `retry.retry_delay_429_ms` | 每次 429 后固定 Sleep | 不读取 Retry-After，不感知 Context |
| `retry.consec_error_threshold` | 单 Key 跨请求暂停阈值 | 429 实际比配置阈值晚一次触发 |
| `failover.consecutive_fail_threshold` | 单请求在同一渠道内累计网络/5xx、提前返回 FailoverError 的阈值 | 并非 ChannelHealth 的阈值 |
| `max_retries` | 未被转发代码使用 | 旧配置，当前无效 |
| `retry_delay_ms` | 未被转发代码使用 | 旧配置，当前无效 |
| `request_timeout_ms` | `http.Client.Timeout`，覆盖连接、Header 和读取完整 Body/流 | 长流也会被该总时长中断 |

`RetryState.lastResult`、`RetryState.lastErr` 当前没有被读写到有效流程；`IsFailoverable`、`IsConsecutiveFailCandidate`、`Channel.MaxRetries()`、`Channel.RetryDelay()` 也没有调用方。这说明旧重试设计与当前实现之间存在遗留接口。

## 8. 问题与缺陷分级

### 8.1 P0：轮转轮数实现与配置语义根本不符

证据：`checkRotationAndTimeout` 每次循环执行 `rs.rounds++`；`rs.excluded` 从创建到返回从不清空。

影响：

- 10 个 Key、默认配置 3 时，最多只尝试 3 次，不会尝试完全部 Key。
- 1 个 Key 首次 429 后，下一次循环直接得到 `no available keys`，不会执行所谓第 2、3 轮。
- 现有 `docs/03`、`docs/06`、`docs/retry-config.md` 关于“每轮尝试所有 Key”“默认最多 3×Key 数量次”的描述不成立。

### 8.2 P0：非轮询策略可能漏选可用 Key

证据：`getNextKey` 调用不带排除条件的 `ch.GetKey()`；项目已经存在 `KeyPool.NextExcluding`，但没有被使用。

- `least-errors`、`least-latency`、`least-rate-limited` 在 Key 状态未变化时会稳定返回同一个最佳 Key。它一旦进入 `rs.excluded`，循环仍会反复拿到它，直到耗尽 `poolSize` 次，然后错误返回 nil。
- `random` 在有限抽样次数内可能重复抽到已排除 Key，从概率上漏掉其他 Key。
- 只有默认轮询策略通常能依靠内部 counter 继续推进。

影响：选择策略一旦从 round-robin 改为其他策略，渠道内容灾重试能力显著下降，并可能出现“明明有可用 Key，却返回 503”。

### 8.3 P0：流解析失败被吞掉并标记成功

证据：

- `accumulateChatStream` 结束后不检查 `scanner.Err()`，JSON 错误直接 `continue`。
- `PipeClaudeStreamToChat`、`PipeGeminiStreamToChat` 同样不检查 scanner 错误。
- 原生流式 `io.Copy` 的返回值被忽略。
- Chat 源转换函数也普遍忽略 scanner 错误和写入错误。

影响：网络中断、单事件超过 1 MiB、上游发送错误格式、空响应或客户端断开，都可能得到 HTTP 200、部分/空内容，并把 Key 标记成功。监控看起来健康，客户端却拿到不完整结果。

### 8.4 P0：跨协议“流式”并非实时流，且合成协议存在兼容风险

影响包括：首字时间接近完整生成时间、长响应内存增长、长流被 `request_timeout_ms` 截断、重试产生重复上游费用、工具调用/推理/finish reason 丢失，以及 Chat/Gemini 合成流格式不符合对应协议预期。

### 8.5 P1：总超时不是硬限制

单次 `HTTPClient.Do` 最长可执行到 `request_timeout_ms`，429 Sleep 也可能越过总上限；检查发生在这些阻塞操作之后。默认 `max_total_wait_ms=30s`、`request_timeout_ms=60s` 时，一次请求就可能超过配置的 30 秒。

跨渠道外层的 `failover.total_timeout_ms` 也只在开始尝试下一个渠道前检查，不能取消当前 dispatch，因此同样是软上限。

### 8.6 P1：错误分类会污染 Key 与渠道健康

- 400 通常和请求参数/转换有关，却累加当前 Key 的连续错误，达到阈值会暂停 Key。
- 其他 4xx 返回的 FailoverError 在外层统一调用 `ReportChannelFailure`；ChannelHealth 注释声称只统计 5xx/连接错误，实际会统计所有 FailoverError。
- ChannelHealth 阈值固定为 3，并非全局 failover 配置。
- FanoutStream 的正常取消可能被记为网络错误。
- `On401` 不增加 RequestCount，与其他错误统计口径不一致。

### 8.7 P1：延迟与最小延迟策略相互污染

- 原生、Chat 源流式、跨协议流式链把包含前序失败和 Sleep 的总耗时记给最终 Key。
- 错误请求通常增加 RequestCount，却不增加 TotalLatency；平均延迟分母包含部分失败、分子只含成功路径，失败越多反而可能让平均值偏低。
- 这些值直接参与 `least-latency` 选择，可能形成错误反馈。

### 8.8 P1：响应大小限制不能检测截断

所有 `io.LimitReader(resp.Body, limit)` 都只读 limit，不读取 `limit+1`，无法判断上游是否超限。结果可能是：

- 非流式 JSON 被静默截断，随后报转换错误或把部分数据发给客户端。
- 错误体最多可能达到 64 MiB 并进入日志/错误响应。
- 流式汇聚完全没有总大小限制。

### 8.9 P1：响应 HeaderPolicy 在转换流路径中执行过晚

在 `streamFromChatSource`、`streamChainConversion`、`fanoutStreamForward` 中，HeaderPolicy 位于 flusher 内，首次执行时状态码已经写出。配置的响应 Header 增删改通常不会对客户端生效。

### 8.10 P2：四套复制代码已经发生行为漂移

已确认的漂移包括：

- 转换后非流式的 401 不清零 `consecFails`，其他三套会清零。
- 错误体上限有“配置大小”和固定 64 KiB 两种。
- 失败日志详细程度不同，流式两套缺少 native 中的 Key 排除原因日志。
- 延迟有“最终单次请求”和“整个重试周期”两种口径。
- 错误响应 Body 有的先读，有的直接关闭，连接复用行为不同。

继续复制分支会使修复难以保持一致。

### 8.11 P2：暂停与 429 存在边界问题

`KeyState.On429` 在判断阈值后才执行 `ConsecErrors++`。默认阈值 3 时，第 3 次 429 不暂停，第 4 次才暂停；其他错误是先加一再判断，第 3 次即暂停。

暂停到期后虽然策略选择阶段通常会 `ResetPause`，但 KeyPool 前半段的 `hasExpiredPaused` 分支逻辑与 `IsAvailable` 的返回值存在互斥，属于冗余且容易误导的状态处理。成功时 `OnSuccess` 也只清连续错误，不主动清 `Paused/PauseUntil`，依赖选择阶段先重置。

### 8.12 P2：深度日志和状态记录不完整

- 转换后非流式成功后调用 `LogUpstreamResponseHeader(result.StatusCode, nil)`，没有使用已保存的 `result.Headers`。
- FanoutResult 根本不保存 Header。
- 401、429、5xx 多数路径不记录响应 Body，排查真实上游原因困难。
- native 请求日志的最终状态固定写 200，即便实际上游成功状态不是 200。

## 9. 现有文档偏差

需要特别注意，以下文档描述的是设计意图，不是当前事实：

- `docs/06-重试与Key管理策略.md`：声称全部 Key 排除后会清空排除表并开始下一轮；代码没有该行为。
- `docs/retry-config.md`：声称默认最多尝试 `3 × Key 数量` 次；代码最多尝试 3 次。
- `docs/03-使用说明书.md`：声称超时后返回最后一个上游响应；`RetryState.lastResult` 未使用，实际返回通用 503/504/FailoverError。
- `docs/06`、`docs/11`：声称其他 4xx 在渠道内换 Key；代码立即返回 FailoverError。
- `docs/03`：仍描述 `max_retries`、`retry_delay_ms`，当前转发路径没有使用它们。

在修复代码前，不建议仅修改旧文档为某一种期望语义；应先明确产品要的是“最大总尝试次数”还是“完整轮转次数”，否则配置兼容性无法判断。

## 10. 测试覆盖现状与缺口

当前测试主要覆盖：

- 五种入口的上游 400 映射为 503，并保留错误原因。
- 单渠道 401 最终返回 JSON 错误。
- 转换后 Fanout 返回目标协议格式。
- SSE Usage 捕获和部分 Responses 流转换。

未发现针对以下核心行为的测试：

2. 多 Key 下 401/429/5xx/网络错误的选择顺序。
3. 所有 KeyStrategy 与请求内排除表的组合。
4. 429 达到暂停阈值的边界。
5. scanner 错误、超大 SSE event、缺少 `[DONE]`、空流、半截 JSON。
6. 客户端取消和 429 Sleep 的及时退出。
7. 响应体超过上限时的明确错误。

9. Fanout loser 取消是否错误累加 Key 健康计数。
10. 合成 Chat/Responses/Claude/Gemini 流的协议一致性。

## 11. 后续修改建议（本轮未实施）

建议按以下顺序推进，避免同时改变过多外部行为：

1. 先确定配置契约：把 `max_rotation_rounds` 恢复为真正轮数，或新增/改名为 `max_attempts` 并制定兼容策略。
2. 抽取唯一的渠道内 Attempt 状态机，让四套路径共享 Key 选择、状态码分类、Body 关闭、超时和统计规则。
3. Key 选择必须在策略选择前过滤请求内 excluded；评估复用并补全 `NextExcluding`。
4. 使用 Context deadline 覆盖整个渠道内重试；429 等待用 timer + select，可响应取消和剩余预算。
5. 明确 400、401、403、404、409、422、429、5xx 的“Key 级/渠道级/请求级”分类，避免请求错误污染 Key。
6. 所有读取和写入都检查错误；响应大小使用 `limit+1` 明确拒绝超限。
7. 决定跨协议流要“真正增量转换”还是明确降级为非流式；若继续合成流，逐协议补齐标准事件和字段。
8. 统一延迟定义：至少分为单次上游 TTFB、单次完整耗时、整个请求重试耗时，不再混用。
9. 修复 Fanout 正常取消的统计，并把赢家成功推迟到流完整处理之后。
10. 先补状态机表驱动测试与协议金丝雀测试，再实施重构。
